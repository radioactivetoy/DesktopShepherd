# Code review and plan (2026-11-21)

Full read of `src/` (about 7,000 lines), the docs and `%APPDATA%\DeskBoxes\log.txt`. Nothing was
changed in the code. Problems are ranked by how much they hurt stability, speed and memory.

---

## 1. The Win+D bug (boxes disappear on "Show desktop")

### What the code does today
`desktop::watch_show_desktop` gets a notice from Windows each time a new window comes to the
front. If that window is the desktop (`Progman` or `WorkerW`), every box is put "just above the
desktop" right away, then again 120 ms and 400 ms later (`send_to_bottom`). The log shows the
notice does arrive (`desktop to front: Progman, 7 boxes`), so the watcher works. The part that
fails is putting the boxes back in view.

### Test result (2026-11-21, later the same day)
With **this project's build**, `tools/test_show_desktop.ps1` shows every box above the desktop
and visible 300 ms and 2 s after Win+D, in three runs, and a screenshot taken during Show desktop
shows all boxes. The disappearing boxes came from an **older build** that was running from
`Downloads\Craft Anything\app`. No code change was needed. The topmost approach below stays as
the fallback if the problem ever comes back on another Windows build.

### Follow-up: the remaining blink (deferred)
A guard thread now cuts the covered time per Win+D from ~120 ms to ~8–12 ms (see STATUS). The
two ways to remove it completely are **parked, to be revisited only if needed**:
1. Injection into Explorer (what Fences does). Weeks of work, and a bug crashes Explorer.
   Against hard rule 1.
2. Making boxes child windows of Explorer's desktop (what wallpaper apps do). There is no code
   in Explorer, but input gets linked to it, and glass support is unknown. If ever tried: about
   a day to prototype, on a test copy, behind a setting.

### Possible causes considered before the test
1. **The desktop may be lifted into the "always on top" layer during Show desktop.**
   `send_to_bottom` walks up from the desktop and skips every always-on-top window. If the desktop
   is in that layer itself, the walk runs off the end and the box goes to `HWND_TOP` of the
   *normal* layer, which is still under the desktop. The box stays hidden.
2. **Timing.** Explorer may lift the desktop in more than one step, or later than 400 ms (it
   animates). Our last fix-up happens before Explorer is done.
3. **The boxes are being hidden, not covered.** Show desktop may minimise or "cloak" (DWM-hide)
   our windows. The classic path has code that un-minimises boxes, but the DirectX boxes
   (`host.rs`) don't have it.

### The fix to build (no hooks into Explorer, no Explorer coupling)
This is the method Rainmeter uses for its "on desktop" skins. It has been reliable for years.
- Keep the existing foreground notice (it is already out-of-process and safe).
- **When the desktop is in front:** make every box *always-on-top* for that moment
  (`SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE | SWP_ASYNCWINDOWPOS)`). It then shows above the
  lifted desktop, whatever layer the desktop is in.
- **When any other window comes to the front:** take always-on-top off again and put the boxes
  back at the bottom (`HWND_NOTOPMOST` followed by today's `send_to_bottom`).
- Check whether the window in front is really the desktop (it contains `SHELLDLL_DefView`), not
  just its class name.
- If test cause 3 is confirmed, also un-minimise and un-cloak DirectX boxes.
- Don't do the "parent the boxes to Explorer's desktop window" trick that wallpaper apps use. A
  window owned by Explorer shares Explorer's input queue, so if our app ever hangs, the desktop
  hangs with it. That breaks hard rule 1.

## 3. Performance and memory (top priority)

### P1 — Biggest CPU/GPU waste: every box redraws when any box changes
`show_fences` calls `HostSystem::frame` for **every** box on **every** update. `frame` always runs
egui, builds all triangles, uploads them to the GPU and calls `Present`. So:
- moving the mouse over one box redraws all 7 boxes, ~60 times a second;
- the clock's once-a-minute tick redraws all boxes;
- a blinking text cursor in the note widget redraws all boxes twice a second while it has focus;
- every desktop re-read that finds a change redraws all boxes.

The docs say "only boxes with changes repaint", but the code doesn't do that yet.

**Fix:** each box keeps its own "next redraw time". A box draws only when (a) it received mouse or
keyboard input, (b) its own timer is due (egui reports one per viewport: `repaint_delay` in
`viewport_output`), (c) its contents changed (new scan, icon loaded, layout edit), or (d) a
resize or move. Everything else is skipped, with no egui pass and no `Present`. Also set the
composition properties (size, corners, tint, blur) only when they change. Today they are set
every frame, and each change makes Windows recompose. **Expected:** mouse-over CPU drops by
about the number of boxes (7×); idle stays at ~0.

### P2 — Per-frame waste inside a box redraw
- `visible_tabs` copies every item (`DeskItem` clone) and re-sorts with fresh lower-case strings
  each frame. The auto-sort box does this for the whole desktop. Cache the sorted list per box,
  and rebuild it only when the scan or the layout changes.
- `fence.clone()` (all tabs and paths) and the `claimed` set are rebuilt every frame. Same fix.
- `d3d.rs` builds the vertex buffer byte by byte (`extend_from_slice` per field). egui's vertex
  is already the exact 20-byte layout, so copy the slice in one go. Reuse the `Vec`s, and keep
  one render-target view per swap chain instead of creating one per frame.
- `Present(1, …)` waits for the screen's refresh. With several boxes drawing in one pass, the UI
  thread can wait once per box. Use `Present(0)` (DWM syncs composition swap chains anyway), or
  `SetMaximumFrameLatency(1)` and present once per box.

### P3 — Memory
- **GL main window ≈ 90 MB** for an invisible 1×1 window (already idea 1 in STATUS). This is the
  biggest memory win, and it also removes S1/S2. Use a plain Win32 message loop for the DirectX
  path, and start GL only when the settings window or the classic fallback is needed.
- **Icons load at 2× size.** At 100 % scaling, a 48 px icon is stored at 96 px (4× the memory).
  Use `icon_size × display scale`. Old sizes are never dropped after a View change. Keep only the
  sizes in use.
- **The fonts are loaded twice.** `setup_style` reads Segoe UI and Segoe Fluent Icons from disk
  for both egui contexts, which means two copies and two font atlases. Read them once and share
  the same `Arc`.
- **The layout preview's icon cache** (`preview_icons`) stays after the settings window closes.
  Drop it on close.
- **The sketch widget** keeps every point forever in `layout.json` (saved pretty-printed). Thin
  out the points (drop ones closer than ~2 px), and save the JSON compactly.
- `UiState` maps (`hwnds`, `sizes`, `burst`, `icon_rects`, `rounded`, `focused`) keep entries
  for deleted boxes. It's tiny, but it should be cleaned in `Act::DeleteFence`.

### P4 — Background wake-ups (small, but they add up over a day)
- The desktop folder is re-read every 4 s (two file-system calls per item). Use
  `ReadDirectoryChangesW` on the two desktop folders instead (already idea 4). The monitor check
  can come from `WM_DISPLAYCHANGE` instead of every 4 s.
- The wallpaper thread still wakes every 10 s on the DirectX path, where it is not needed at all.
  Don't start it unless the classic path is in use.
- Every desktop click starts a new short-lived thread in the Win+D watcher. Use one thread with
  a channel, or `SetTimer` on the UI thread.

## 4. Smaller bugs and rough edges
- `show_in_folder` uses `explorer /select,<path>`, which breaks on paths with commas. Use
  `SHOpenFolderAndSelectItems`.
- The keyboard map (`host.rs key_of`) has no Page Up/Down, F2 (rename) or digits, and
  `WM_SYSKEYDOWN` (Alt combos) is not handled. That limits widgets that take typing.
- The settings line "`{} icons loaded · {} desktop items`" prints the same number twice
  (`app.rs:2211`).
- `prepare_box` subclasses DirectX box windows a second time. Their own window procedure already
  handles no-activate, so it's harmless but redundant.
- The unused `mut` warnings mentioned in STATUS.

## 5. Getting ready for more widgets and customisation
- `(kind.make)()` creates a widget object on every frame. Fine for today's three, but give
  widgets a persistent instance per box (kept in `UiState`) so later widgets can hold caches
  (decoded images, system stats).
- Give each widget a "how often I need to redraw" contract that works with the per-box timer
  from P1. A system-monitor widget at 1 s must not redraw the other boxes.
- Before adding more look options, move the look settings (`color`, `alpha`, `corner`, `blur`,
  border, fonts) into one `Look` struct inside `Fence` with `#[serde(default)]`. That needs a
  v4 migration in `sanitize` (hard rule 6).

## 6. Direction (decided 2026-11-21)

The foundation is right: our own process, no Explorer injection, real composition glass, a
supervisor, Rust. The weak part is the **eframe/GL main window** left over as a 1×1 invisible
"engine" (≈90 MB, the start failures, and all boxes redrawing together), plus a second complete
**classic** drawing path that is costly to keep working.

Target architecture:
1. **Own the main loop**: a plain Win32 message loop drives the boxes; each box redraws only
   when it changed.
2. **One drawing path**: settings window and menus are drawn with the same D3D11 renderer as
   the boxes. Old GPUs / Remote Desktop use Windows' software DirectX (`D3D_DRIVER_TYPE_WARP`)
   instead of the classic GL path, which then goes away (`wallpaper.rs`, most of `ghost.rs`).
   Note: this replaces hard rule 5 ("keep the classic GL path") – update CLAUDE.md/GEMINI.md
   when it lands.
3. **Keep egui** for the contents of boxes and windows.
